# Schedule Hub 全体構成設計

## 1. 目的

本書は、Schedule Hub MVPのAWS全体構成を定義する。

前提は以下のとおり。

- 利用者は自分と親しい少人数を想定する。
- 正式対応チャットはClaude公式チャット。
- Remote MCP経由で予定作成を行う。
- Web設定画面のみ提供する。
- Google Calendarへ直接登録する。
- TimeTree個人利用・Yahoo!カレンダーはGoogle CalendarをBridgeとして表示する。
- MVPではcreateのみ対応する。
- AWS構成は運用負荷とコストを抑えることを優先する。

## 2. 採用AWSサービス

| サービス | 用途 |
|---|---|
| Amazon S3 | Web設定画面の静的ファイル配置 |
| Amazon CloudFront | S3上のWeb SPAをHTTPS配信 |
| Amazon API Gateway | Web API / MCP / OAuthエンドポイントの公開 |
| AWS Lambda | MCP、Web API、Google OAuth処理 |
| Amazon DynamoDB | ユーザー設定、Calendar Mapping、OAuth情報、操作履歴 |
| Amazon Cognito | Schedule Hubユーザー認証、Claude接続時のユーザー識別 |
| Amazon CloudWatch | Lambda / API Gatewayのログ・メトリクス確認 |

MVPでは以下は採用しない。

- Route 53
- ACM
- AWS WAF
- Secrets Manager
- Customer Managed KMS Key
- VPC / NAT Gateway
- ECS / Fargate
- RDS / Aurora
- SQS / Step Functions

AWS標準URL、AWS管理の保存時暗号化を利用する。

## 4. コンポーネント責務

### 4.1 S3

Web設定画面の静的ファイルを保持する。

想定フロントエンドはSPAとする。

主な画面:

- ダッシュボード
- Googleアカウント設定
- Logical Destination設定
- TimeTree / Yahoo表示設定
- 予定デフォルト設定
- Claude接続ガイド
- 操作履歴

### 4.2 CloudFront

S3上のWeb SPAをHTTPSで配信する。

MVPではCloudFront標準ドメインを利用する。

```text
https://dxxxxxxxx.cloudfront.net
```

独自ドメインは使用しないため、Route 53 / ACMは不要とする。

### 4.3 API Gateway

外部公開エンドポイントを集約する。

想定パス:

```text
/mcp
/api/*
/google/oauth/start
/google/oauth/callback
```

MVPではAWS標準のexecute-api URLを使用する。

### 4.4 MCP Lambda

ClaudeからのRemote MCPリクエストを処理する。

MVP Tool:

- `get_schedule_context`
- `create_schedule`

責務:

- 認証済みユーザーの特定
- MCPリクエスト解析
- UserPreference取得
- Logical Destination取得
- Destination検証
- Logical → Physical Calendar解決
- Physical Calendar重複排除
- Google Calendar登録
- 冪等性管理
- 成功 / 部分成功 / 失敗の集約

### 4.5 Web API Lambda

Web設定画面からのAPIを担当する。

主な責務:

- UserPreference取得・更新
- Logical Destination CRUD
- Alias / 用途説明設定
- Physical Calendar Mapping設定
- External Display設定
- Google Calendar一覧取得
- 操作履歴取得

### 4.6 Google OAuth Lambda

Google OAuthフローを担当する。

責務:

- OAuth開始URL生成
- `state`生成・保存
- callback検証
- authorization code → token交換
- GoogleConnection保存
- Google Calendar一覧同期

### 4.7 Cognito

Schedule Hubユーザーを一意に識別する。

Web設定画面とClaudeからのMCP利用で同一ユーザーを紐付けられる構成とする。

基本的にはCognito `sub`をSchedule Hubのユーザー識別子として利用する。

### 4.8 DynamoDB

以下のデータを保持する。

- User
- UserPreference
- GoogleConnection
- PhysicalCalendar
- LogicalDestination
- DestinationMapping
- ExternalDisplayTarget
- CreateOperation
- ExternalEvent
- OAuthState

詳細なPK / SK設計はDynamoDB論理設計で定義する。

### 4.9 CloudWatch

最低限以下を確認可能とする。

- Lambda Error
- Lambda Duration
- API Gateway 4xx / 5xx
- create_schedule成功数
- partial_success数
- Google API Error
- Google OAuth Error

Token、Google refresh token、Claude会話全文はログ出力しない。

## 5. 外部サービスとの接続

MVPでAWSから直接接続する外部サービスは以下とする。

```text
Claude
Google OAuth
Google Calendar API
```

TimeTree / Yahoo!カレンダーへAWSからAPI通信は行わない。

```text
Schedule Hub
   |
   v
Google Calendar
   |
   +--> TimeTree外部表示
   |
   +--> Yahoo/LINE外部表示
```

## 6. Logical / Physical分離

ClaudeにはLogical Destinationのみを公開する。

例:

```text
work
private
couple
```

AWS内部では以下のように解決する。

```text
work
 |
 v
DestinationMapping
 |
 v
PhysicalCalendar
 |
 v
Google calendarId
```

Claudeには以下を渡さない。

- Google calendarId
- Google Account ID
- Google OAuth Token
- Bridge Calendar内部構成

## 7. ネットワーク方針

MVPではLambdaをVPCに入れない。

理由:

- DynamoDBはAWS公開エンドポイントを利用できる。
- Cognitoも公開サービス。
- Google APIはインターネット経由。
- RDS等のVPC内リソースを使用しない。

そのため以下は不要とする。

- Private Subnet
- NAT Gateway
- Security Group
- VPC Endpoint

## 8. Secret / 暗号化方針

MVPではSecrets Manager、Customer Managed KMS Keyは使用しない。

Google OAuth Client ID / Client Secret等はLambda環境変数で管理する。

Google Refresh Token等はDynamoDBへ保存する。

最低限以下を守る。

- SecretをGitHubへコミットしない。
- TokenをCloudWatch Logsへ出力しない。
- DynamoDBへのアクセス権限はLambdaに限定する。

AWS標準の保存時暗号化を利用する。

## 9. Lambda構成

MVPでは以下3Lambdaを基本とする。

```text
McpLambda
WebApiLambda
GoogleOAuthLambda
```

共通ロジックはHandlerへ直接実装せず、Application / Domain層へ分離する。

```text
Lambda Handler
    |
    v
Application Service
    |
    v
Domain
    |
    v
Repository / GoogleCalendarAdapter
```

将来的にECS/Fargateへ移行してもDomain Logicを再利用可能とする。
