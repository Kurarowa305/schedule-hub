# Schedule Hub データフロー設計

## 1. 目的

本書は、Schedule Hub MVPにおける主要データフローと各コンポーネントの責務境界を定義する。

基本方針:

- Claudeは自然言語解釈とLogical Destination判定を担当する。
- Schedule HubはLogical Destinationの検証、Physical Calendar解決、Google Calendar登録を担当する。
- GoogleのcalendarIdやOAuth TokenはAWS内部のみで扱う。
- TimeTree / Yahoo!カレンダーへAWSから直接通信しない。
- 曖昧な予定はcreate前にClaudeがユーザーへ確認する。

## 2. データ境界

### Claudeが扱うデータ

- title
- start / end
- timezone
- location
- description
- Logical Destination ID
- Destinationの名称 / Alias / 用途
- 推論理由

### AWS内部のみで扱うデータ

- Cognito userId
- Google Account識別子
- Google calendarId
- Google OAuth access token / refresh token
- Logical → Physical Mapping
- Google Event ID
- CreateOperation
- ExternalEvent

## 8. DF-04 Logical Destination設定

ユーザーはWebで以下を設定する。

```text
名称: 仕事
Alias: 会社 / 業務 / work
用途: 会議・出社・顧客対応等の仕事予定
登録先: Google Work Calendar
```

保存データ:

```text
LogicalDestination
- destinationId
- userId
- name
- aliases
- description
- isDefault
- enabled
```

Mapping:

```text
DestinationMapping
- destinationId
- physicalCalendarId
```

Logical Destinationは1つ以上のPhysical Calendarへマッピング可能とする。

## 11. DF-07 自然言語解釈・曖昧確認

Claudeはユーザー入力と`get_schedule_context`の結果から予定情報・Destinationを推論する。

判定優先順位:

1. ユーザーがDestinationを明示
2. Alias一致
3. 用途説明から意味推論
4. 指定なしならデフォルトDestination
5. 一意に判断できなければ確認

例:

```text
明日10時から顧客との定例
```

`work`の用途説明と一致するため、Claudeは`destinationIds=["work"]`と判断する。

一方、

```text
明日彼女と水族館
```

で開始時刻が不明なら、createせずClaudeが確認する。

```text
何時からにしますか？
```

## 12. DF-08 create_schedule

Claudeからの入力例:

```json
{
  "title": "顧客との定例",
  "start": "2026-08-14T10:00:00+09:00",
  "end": "2026-08-14T11:00:00+09:00",
  "timezone": "Asia/Tokyo",
  "destinationIds": ["work"],
  "destinationInference": {
    "type": "semantic",
    "reason": "顧客との定例のため"
  }
}
```

内部処理:

```text
Claude
 |
 | create_schedule
 v
API Gateway
 |
 v
MCP Lambda
 |
 +--> 1. userId取得
 +--> 2. Input Validation
 +--> 3. 冪等チェック
 +--> 4. UserPreference取得
 +--> 5. Logical Destination検証
 +--> 6. DestinationMapping取得
 +--> 7. Physical Calendar解決
 +--> 8. Physical Calendar重複排除
 +--> 9. GoogleConnection取得
 +-->10. access token確認 / refresh
 +-->11. Google Calendar create
 +-->12. CreateOperation / ExternalEvent保存
 +-->13. 結果集約
 |
 v
Claude
```

## 13. 入力補完

最低限必須:

- title
- start
- destinationIds

補完可能:

- `end`がない → `defaultDurationMinutes`から算出
- `timezone`がない → UserPreferenceから補完

不正なDestination IDはサーバー側で拒否する。

## 16. 複数Calendar登録

複数Physical Calendarへの登録は並列実行を基本とする。

```text
                    +--> Google Work
create_schedule ----+--> Google Personal
                    +--> Google Couple
```

Physical Calendar単位で結果を記録する。

```text
ExternalEvent
- operationId
- physicalCalendarId
- externalEventId
- status
- errorCode
```

## 17. 結果集約

全成功:

```json
{ "status": "success" }
```

一部失敗:

```json
{
  "status": "partial_success",
  "results": [
    {"destinationId": "work", "status": "created"},
    {"destinationId": "private", "status": "failed"}
  ]
}
```

全失敗:

```json
{ "status": "failed" }
```

Claudeへ返すレスポンスにはGoogle内部IDを必要以上に含めない。

## 18. DF-10 冪等性

create開始時にCreateOperationを作成する。

状態:

```text
PROCESSING
   |
   +--> SUCCESS
   +--> PARTIAL_SUCCESS
   +--> FAILED
```

同一operationIdが既に完了済みの場合、Google Calendar APIを再度呼ばず既存結果を返す。

Google側でも`operationId + physicalCalendarId`を基に決定的Event IDを生成することで、Lambda timeout等による二重作成を抑止する。

補助情報としてeventHashを保持可能とする。

```text
eventHash = hash(userId + title + start + end + sorted(destinationIds))
```

ただしeventHash単独では重複判定しない。

## 19. operationId方針

MCPクライアントのrequest IDを安定して再利用できる場合はそれをoperationIdへ利用する。

再送時にrequest IDが変化し得る場合は、MCP Lambdaで独自operationIdを発行し、再試行設計を別途詳細化する。

最終方式はMCP Tool Schema設計時に確定する。

## 20. DF-11 TimeTree / Yahoo表示

AWSからTimeTree / Yahooへ直接通信しない。

```text
Schedule Hub
 |
 v
Google Calendar
 |
 v
OS Calendar同期
 |
 +--> TimeTree Home
 +--> Yahoo/LINE Calendar
```

Schedule Hubが保証できるのはGoogle Calendarへの登録成功までである。

そのためUIでは以下のように表現する。

```text
TimeTree: 表示元Google Calendarへの登録成功
Yahoo:    表示元Google Calendarへの登録成功
```

「TimeTree登録成功」「Yahoo登録成功」とは表現しない。

### McpLambda

- `create_schedule`

- 冪等性

### GoogleOAuthLambda

- OAuth Start
- OAuth Callback
- GoogleConnection保存
- Calendar同期

## 24. データフロー設計上の固定事項

1. ClaudeはPhysical Calendarを知らない。
2. Google OAuth TokenはAWS外へ出さない。
3. TimeTree / YahooへAWSから通信しない。
4. 曖昧判定はcreate前に行う。
5. Destination判定はClaude、Destination存在検証はSchedule Hubが行う。
6. create結果はPhysical Calendar単位で保持する。
7. 操作は冪等にする。
